# Bug review — chart not loading + signal volume (2026-09-24)

Method: 5 read-only diagnosis lenses (web chart windows, server + phone, engine, pipeline, uncommitted-diff regression sweep) → one adversarial verifier per finding (38 verdicts, 35 confirmed) → ranked report. Evidence: signal_history/cached_candles read-only queries, browser network log, server log, payload measurements.

## Chart root cause

The visible terminal chart is not the problem: on every page load the ALWAYS-mounted hidden engine page (client/src/pages/market.tsx, kept alive under the terminal by App.tsx) derives its candle window from scrubber indices that start at 0..59 and from a 730-day fallback, so for two intermediate renders it asks the server for 1m/5m/60m candles from 2019-08-04 (the first cached day, from=1564876800) and from now-730d (from=1727189845), each URL twice because raw1m/bg1m (and bg5m/bg15m, raw60m/bg60m) use different react-query keys, and none of those fetches pass an AbortSignal so they all complete. Because the store now holds 2.47M MES 1m rows back to 2019 and server/routes.ts applies SERVE_CAP only when `from` is absent, each 2019 request serializes 248 MB for ~20 s on the single-threaded server (twice) plus 71 MB x2 for the 730-day one, freezing ticks/WS/every poll while the browser main thread parses ~660 MB of JSON — the terminal's own sane 10-day 1m fetch (useTerminalData.ts FAST_OPEN_DAYS) simply queues behind that stall after `setCandles([])`, which is the empty chart, the '—' HUD and 'waiting for candles…'. Not a regression of the uncommitted diff (HEAD has the identical window code); the trigger is store growth. A fix for the client (candle-window.ts + market.tsx) and the server (serve-window.ts + routes.ts clamp) already sits UNCOMMITTED in the working tree (edited 12:44-13:32 ET today by a concurrent session, after the user said not to implement suggestions); the browser gets the client half on reload via Vite, but the node server (pid started 10:50:25 AM, plain tsx, no watch) still runs the old route until restarted, and the new files are untracked.

## Signal-volume root cause

DESIGN (roughly 75-80% of the volume, ~100-150 rows/day, 84% overnight, pre-dating the current diff): the primary Yellow Box 'break' fact is a per-bar STATE — shared/fact-engine.ts pushes a counted DRIVER fact on EVERY closed bar whose close sits outside the day box (today 909 of 1117 session bars closed below 7765.52) — and its usual partner (Fractal FCO-trending / band / 5-bar breakout) is also a state, so 2 counted facts + a driver exist on every bar, the gate ALLOWS Fr+YB@1m (n=2818, PF 2.08, judged on an ETH-dominated population that is net -507 pts over 30 days), COOLDOWN_BARS is 4 (not the 10 CLAUDE.md documents; 4 since the fact engine's first commit) and ETH_CONFLUENCE (user directive 2026-08-11) runs the block all night, so the engine fires at the cooldown floor every 4-10 minutes for as long as a trend stays outside the box (32 consecutive 1m fires exactly 240 s apart today; 96 Short / 4 Long is a -52 pt one-way night under the box, not a stuck state). BUG (the remaining ~20-25%, and the data-integrity damage): three writers — the 10-min catch-up replay, the server live engine and the browser tab's 2-day 'live edge' persist — each run their own cooldown cursor over slightly different candle snapshots and dedupe against the DB only by exact (interval,timestamp,direction), so phase-shifted replays UNION into signal_history (37 same-interval pairs closer than the 4-bar cooldown today, including the SAME catch-up code shifting its whole fire lattice by one bar after an MW backfill rewrote the store); and the tab re-POSTs ~200 rows on every reload stamped source='live', which the POST route upgrades permanently (catch-up 97 / live 3 became live 105 / catch-up 24 within minutes), locking backfilled rows against regen and hiding provenance. The '600-700 open rows' in the evidence was a misread (the stuck-row resolver's denominator counts closed win_tp1 rows; real open rows are single digits), and the overnight rows were back-filled at 8:36 AM on Yahoo's 985-bar backfill after a 17-hour laptop standby — the catch-up doing its documented job, not the live engine.

## Ranked bugs

### 1. [critical] Hidden engine page fetches candles from 2019 and from now-730d on every page load (transient windows, never aborted)

- Where: `client/src/pages/market.tsx:746`
- Mechanism: startDayIdx/endDayIdx start at 0/59 and are corrected only by a passive effect after the render in which /api/data/cached-days arrives, so that render's windowedDays = the OLDEST 60 days (2019-08-04) and fromTs = 1564876800; before cached-days arrives fromTs = fallbackFromTs = now-730d; every candle query is enabled by `fromTs > 0` only and the queryFns ignore react-query's `signal`, so the giant requests complete and are JSON.parsed anyway. This page IS the always-mounted engine, so it happens on every terminal load. Combined with bug 2 that is 2x248 MB + 2x71 MB per load.
- Fix: Derive the window synchronously: while indices are unsettled, windowedDays = sortedDays.slice(-windowSize) (never days[0..]); return fromTs = 0 while cached-days is loading so the queries stay disabled (keep a small 10-day fallback only for the cached-days-failed case); pass `{ signal }` into every cached-continuous fetch so a superseded key aborts. NOTE: this exact fix already exists uncommitted on disk (client/src/lib/candle-window.ts + market.tsx dayWindowSettledFor / windowStartTs / fetchContinuousWindow(signal)); it needs review + commit, not re-implementation. Do NOT add gcTime:0 (staleTime Infinity relies on the cache for instant interval switches).
- Test: scripts/cached-continuous-cap.test.ts (already on disk, 109/109 passing) covers 'never the FIRST cached day' and the fallback; plus browser check: reload localhost:3000 with Network open and assert no /api/data/cached-continuous request has from < dateToTs(days[len-windowSize]) and no day-zones response with {days:1837}/{days:519}; server log must show no cached-continuous/MES/1m line over ~1 s per load.

### 2. [high] Server SERVE_CAP is bypassed by any explicit `from` (including negative/garbage) — one deep request serializes 2.47M rows for 14-29 s on the single thread

- Where: `server/routes.ts:1224`
- Mechanism: `if (!fromN)` is the only place the 250k-row OFFSET cap runs; any truthy from (2019, -1, 1e3) reads every row with no LIMIT, runs the filter chain and JSON.stringify synchronously (248 MB), and bodies >12 MB are never cached so the duplicate pays again. Logged 13 times today at 13.6-29.1 s each, with /api/live/candles, day-zones and news queued 5-26 s behind. Ticks, WS broadcasts and the order path share that thread.
- Fix: Clamp always: compute the cap floor (reuse servedFloorFor) and `fromN = Math.max(Number.isFinite(fromN) ? fromN : 0, capFloor)`, set servedFloorTs only when it trims, before the hour-floor; memoize the floor per (sym,res) ~60 s or only check when fromN is older than ~120 d so hot short-window requests pay nothing; normalize `to` the same way (NaN -> Infinity then clamp). NOTE: already implemented uncommitted on disk as server/serve-window.ts + routes.ts:1224-1234 (span caps 1m/5m 150 d, 15m 400 d) — but the running server predates the edit and still serves the old route; it needs a restart in a quiet window and the untracked files committed.
- Test: Against a RESTARTED server: GET /api/data/cached-continuous/MES/1m?from=1564876800 (and from=-1, from=abc, from=1e3) returns candles.length <= 250k (or the 150 d span), capped/servedFloorTs set, body < 30 MB, < 3 s; a 3-day from returns the identical body as today with servedFloorTs null; scripts/fact-engine-parity.test.ts still green (90-day engine windows are never clamped).

### 3. [high] Background queries duplicate identical URLs (1m, 5m, 60m each fetched twice per window) because the 'bg' key suffix defeats react-query dedup

- Where: `client/src/pages/market.tsx:2066`
- Mechanism: raw1m [..,'1m',from,to] and bg1m [..,'1m',from,to,'bg'] fetch the same URL; likewise raw60m/bg60m, and bg5m/bg15m both GET /5m. react-query keys the cache by hash only, the server has no in-flight coalescing and never caches bodies >12 MB, so every window costs two serializations and two parses — the 2x multiplier on bugs 1-2 and still ~10 MB x2 per interval after they are fixed.

(The uncommitted working tree already shares q1mData between raw1m/bg1m.)
- Test: Fetch-spy on the default 15m view: exactly one request per (interval URL, from) pair; on the 5m view exactly one /5m request and bg15mCandles deep-equals agg5mTo15m(that response); after a ranged setQueryData splice on the 5m key bg15mCandles reflects the spliced rows; npm run check clean.
